# ADR-0034: Классы игроков — Инженер и Техно-оккультист

- **Статус:** Accepted · 2026-11-22 (S6-01, план и уточнения 1–9 подтверждены владельцем проекта)
- **Связано:**
  - [ADR-0005](ADR-0005-profile-authority.md) — профиль у машины игрока, рейд у хоста;
  - [ADR-0026](ADR-0026-diegetic-visor-resonance-tags-helmet-lamp.md) — визор;
  - [ADR-0030](ADR-0030-raid-inventory-loadout.md) — снимок лоадаута;
  - [ADR-0031](ADR-0031-hub-economy-crafting-shop-insurance.md) — транзакции профиля;
  - [ADR-0033](ADR-0033-hub-screens-commonui.md) — экраны хаба;
  - [Блок 6](../Architecture/06_Phase2_Content_and_Meta_Plan.md) (S6-01).

## Контекст
- **Классов не было.** Все играли одним экзокаркасом: способности шли от `DA_AbilitySet_ExoFrame` и предметов лоадаута, стартовый лоадаут лежал в конфиге.
- **Sprint 6 вводит второй класс.** Нужен общий каркас: что даёт класс, где хранится выбор, кто его подтверждает, как его видит отряд.

## Решение
1. **`UHollowClassDefinition`** — primary asset `HollowClass`, модуль Economy: там же мета-данные профиля, а Game из Economy недоступен.
   - Поля: имя, описание, тег `Hollow.Class.*`, `AbilitySet`, бесконечный эффект атрибутов, стартовый лоадаут, цвет визора.
   - Классы: `DA_Class_Engineer` (класс по умолчанию) и `DA_Class_Occultist`. Их создаёт `create_class_assets.py`.
2. **Выбор класса — данные профиля** (ADR-0005; уточнения 1, 8).
   - `FHollowProfile::ClassId` — играемый класс; `ClassLoadouts` — лоадауты остальных.
   - **Транзакция `SelectClass`** (атомарная, идемпотентная, не во время рейда): текущий лоадаут остаётся за текущим классом, у нового возвращается свой. Склад общий, ничего не покупается и не теряется.
   - **Стартовый лоадаут — один раз**, при первом выборе класса. Отказы: `UnknownClass`, `AlreadySelected`.
   - **Новый профиль** — класс по умолчанию (`DefaultClass` в настройках) и его стартовый лоадаут; прежний `StartingLoadout` в конфиге удалён.
   - **Старый профиль** без класса играет классом по умолчанию со своим лоадаутом, без нового набора и без смены версии сейва.
3. **Класс на сервере** — `UHollowClassComponent` на `AHollowPlayerState`.
   - `ClassId` реплицируется всем (push-модель).
   - Пока класс играется, сервер держит на ASC игрока его набор способностей, эффект атрибутов и тег. Тег — loose, `TagOnly`, виден на всех машинах. При смене класса старое снимается по сохранённым handles.
   - Клиенты узнают о смене через `OnClassChanged` (OnRep).
4. **Кто меняет класс** (уточнение 7).
   - **Хаб.** Клиент применяет `SelectClass` к своему профилю (блок CLASS в шкафчике или `Hollow.Class.Select`). Затем `AHollowPlayerController` шлёт `Server_SelectClass`, когда класс профиля отличается от последнего отправленного — при входе в хаб и при каждом изменении профиля.
   - **Сервер принимает только в хабе и только существующий класс**, иначе мягкий отказ с Warning.
   - **Рейд.** Класс приходит в `FHollowLoadoutSnapshot::ClassId`; хост доверяет ему, как лоадауту. Без класса или с неизвестным — класс по умолчанию.
   - **Seamless travel.** `AHollowPlayerState::CopyProperties` переносит класс в новый `PlayerState`.
5. **Что дают классы** (уточнения 2–5; данные, баланс позже).

   | | Инженер | Техно-оккультист |
   |---|---|---|
   | Эффект | `MaxToolHeat` +25, `Armor` +10 | `ResonanceGainMultiplier` ×0,8 |
   | Набор способностей | пуст: инструменты — предметы | наполнят S6-02 (фонарь — предмет) и S6-03 (Ритуальная печать) |
   | Стартовый лоадаут | сварка (застрахована), резак, 3 ячейки, 2 мины | 3 ячейки (фонарь — S6-02) |
   | Цвет визора | янтарный | сиреневый |

   - Модификаторы выбраны так, чтобы после спавна ничего не требовало дозаливки: `GE_ExoFrame_InitAttributes` задаёт базу, эффект класса модифицирует поверх.
   - Предметы классами не ограничены (уточнение 3): к этому вернёмся после S6-02.
6. **Визор** (уточнение 6). Цвет класса красят строки телеметрии: голос, расходники и строка включённого фонаря. Цвета тревоги Резонанса не меняются.
   - Контекст визора следит за компонентом класса `PlayerState` своего игрока: он приходит вместе с ASC.
7. **Шкафчик.** Блок CLASS над колонками: у каждого класса «Choose», у играемого — «Playing».
   - Скрипт `create_hub_ui_assets.py` вставляет блок в существующий `W_Loadout`.
   - Фокус геймпада никогда не начинается на смене класса: список классов в фокус-порядке последний.

**Сеть:**
- `ClassId` (один `FPrimaryAssetId`) на `PlayerState`, push;
- один Server RPC на смену класса в хабе;
- одно поле в снимке лоадаута;
- тег класса — минимальная репликация ASC.

## Проверка
- **Автотесты:**
  - `Hollow.Economy.Class.{Select, Data}`;
  - `Hollow.Game.Class.SwitchAndReplicate` — два игрока, два класса, разные тег и атрибуты; смена снимает старое точно; `ClassId` реплицируется push-моделью; OnRep клиента; отказ вне хаба; перенос при travel;
  - `Hollow.UI.Hub.Loadout` — блок классов;
  - `Hollow.UI.Visor.ClassColour`;
  - строки классов в `Hollow.UI.Hub.Rules`.
- **Кооп-смоук `playthrough-mac.sh classes`** (150 мс):
  - хост выбирает оккультиста в шкафчике с клавиатуры и геймпада, клиент остаётся инженером;
  - на обеих машинах разные классы, теги, атрибуты и цвета визора — в хабе, в рейде (у хоста лоадаут оккультиста) и после возвращения.

## Последствия
- (+) **Новый класс — это данные:** ассет класса, эффект, набор способностей, стартовый лоадаут. Код не меняется.
- (+) Свой лоадаут у каждого класса: смена класса ничего не стоит и ничего не теряет, поэтому её можно разрешить в любой момент в хабе.
- (−) До S6-02 и S6-03 у оккультиста нет своего инструмента и способностей: класс отличают эффект, тег, цвет и стартовый лоадаут.
- (−) Лоадауты неактивных классов лежат в профиле и в рейд не идут: в эскроу и страховку попадает только активный.
- (?) Ограничения предметов по классам, уровни классов и ветки талантов (бриф §4) — позже.
