# Метрики уровня и стандарт модульного кита (S1-07)

> Источник чисел — `UHollowLevelMetrics` (`Config/DefaultGame.ini`, Project Settings → Game → Hollow Level Metrics). Этот документ объясняет их и описывает правила для автора комнат. Генератор (S2-01), валидатор `HollowRoomRules` и сборщик greybox `Build/Python/create_docks_greybox.py` читают одни и те же значения. Если меняешь число, меняй его в ini; согласованность проверяет тест `Hollow.PCG.LevelMetrics`.

## 1. Числа

| Метрика | Значение | Зачем |
|---|---|---|
| `CellSize` | **400 uu** | клетка грида по X и Y; footprint комнаты — целое число клеток |
| `CellHeight` | **400 uu** | чистая высота этажа: от верха пола до низа потолка |
| `WallThickness` | **20 uu** | стены стоят **внутри** footprint, внешней гранью по его границе |
| `SlabThickness` | **20 uu** | плиты пола и потолка: пол под Z = 0, потолок над Z = `CellHeight` |
| `DoorWidth × DoorHeight` | **300 × 350 uu** | единственный стандартный проём коннектора (решение S1-07, п. 2) |
| `MinCorridorWidth` | **300 uu** | самый узкий чистый проход; коридор в одну клетку даёт 400 − 2 × 20 = 360 |
| `VentSize` | **90 × 90 uu** | вент-люк, проходит только Эхо-Хищник |
| `LargestAgentRadius / Height` | **80 / 280 uu** | навигационный агент Железного Пилигрима (целевой размер, уточним в S3) |

Связанные числа персонажа (не в метриках, они живут в CMC и капсуле): капсула `BP_ExoFrame` r34 / h192 (`create_exoframe_assets.py`), `MaxStepHeight 45` — ступени и рампы кита должны быть ниже.

### Почему 300 × 350
- **Пилигрим:** ширина 2 × 80 = 160 и рост 280 проходят с запасом 70 uu с каждой стороны и сверху, поэтому nav-link через проём не застревает на углах.
- **Кооп-переноска (ADR-0002):** два ExoFrame рядом занимают около 2 × 68 = 136 uu плюс ядро между ними. В 300 uu они проходят, не перестраиваясь гуськом.
- **Перемычка 50 uu** над проёмом (400 − 350) оставляет место под рельс двери или переборки (S3).
- **Откосы по 50 uu** с каждой стороны проёма (400 − 300) / 2: это не меньше толщины перпендикулярной стены, так что в угловой клетке стена соседнего борта не съедает проём. Правило `DoorDoesNotFitCell`: `DoorWidth + 2 × WallThickness ≤ CellSize`.

## 2. Система координат комнаты

```
        +X (North)
          ^
          |   ячейка (1,0) | ячейка (1,1)
          |   ------------ + ------------
          |   ячейка (0,0) | ячейка (0,1)
 origin ->+----------------------------------> +Y (East)
 (угол -X/-Y клетки (0,0,0), верх пола, Z = 0)
```

- Стороны: **North = +X, East = +Y, South = −X, West = −Y** (`EHollowRoomSide`).
- Ячейка `(x, y, 0)` занимает `[x·400, (x+1)·400] × [y·400, (y+1)·400]`.
- В вертикальном срезе **один этаж**: `Footprint.Z = 1`, у коннекторов `Cell.Z = 0`. `FIntVector` оставлен на будущее, чтобы лестницы и шахты не потребовали миграции данных.
- Поворот комнаты генератор делает шагом 90° (`Yaw90` в манифесте, ADR-0003). В комнате ничего не должно зависеть от абсолютной ориентации.

## 3. Коннектор

- Коннектор — это **проём 300 × 350 по центру внешнего ребра клетки**: `FHollowRoomConnector {Cell, Side, AllowedKinds}`.
- Ребро должно быть внешним: North-коннектор только у `x = Footprint.X − 1`, South — у `x = 0`, East — у `y = Footprint.Y − 1`, West — у `y = 0`.
- `AllowedKinds` (битовая маска) — что генератор может поставить в проём: `Door`, `Bulkhead`, `Open`. В соединении двух комнат используется вид, разрешённый обеими сторонами.
- Стены соседних комнат стоят вплотную, поэтому проход сквозь стык имеет глубину 2 × 20 = 40 uu. Дверь или переборку сервер ставит **на общую границу** (плоскость стыка), а не внутрь одной из комнат.
- В уровне комнаты проём — это **дыра в стене**. Створок, рам и триггеров в уровне нет: всё геймплейное спавнит сервер (ADR-0003).

## 4. Сокеты

- `FHollowRoomSocket {SocketType: Hollow.Socket.*, Transform}` в координатах комнаты, по умолчанию на полу (Z = 0). Ось X сокета — направление «лицом».
- Типы: `PlayerSpawn`, `Loot`, `CoreSpawn`, `EnemySpawn`, `VentNode`, `Extraction`.
- Сокеты живут **только в DA** (решение S1-07, п. 6). Маркеров в уровне нет, спавн по ним появится в S2-02.
- Держи сокеты не ближе 100 uu к стенам и не ставь их перед проёмами: ядро и враги не должны перекрывать проход.

## 5. Именование и папки (content-only GFP `HollowSector_Docks`, ADR-0012)

| Что | Путь | Имя |
|---|---|---|
| уровень-оболочка | `/HollowSector_Docks/Rooms/` | `LV_Docks_<Room>` |
| описание комнаты | `/HollowSector_Docks/Data/` | `DA_Room_Docks_<Room>` (primary asset type `HollowRoom`; каталог добавляет `GameFeatureData` плагина) |

На диске: `Plugins/GameFeatures/HollowSector_Docks/Content/`. В Content Browser плагин виден при включённом Show Plugin Content.

Тип комнаты — ровно один тег `Hollow.Room.Type.{Spawn, Extraction, CoreVault, Hangar, Corridor, Junction, Storage}` в `RoomTags`.

## 7. Чек-лист автора комнаты

1. Footprint — целые клетки, один этаж.
2. Каждый проём — 300 × 350 по центру внешнего ребра клетки, и под каждым есть запись в `Connectors`. Других дыр в периметре нет.
3. Стены внутри footprint, внешней гранью по границе; ничего не выступает за footprint (иначе генератор получит пересечения).
4. В уровне только статика, свет и звук. Двери, лут, враги, PlayerStart и триггеры не ставятся. Свет — в бюджете типа комнаты (§9).
5. Ровно один `Hollow.Room.Type.*`, сокеты внутри footprint, у каждого есть тип.
6. Сохрани DA — Data Validation (`IsDataValid` → `HollowRoomRules`) покажет нарушения. Перед коммитом прогони `run-tests-mac.sh --strict` (`Hollow.PCG.DocksRooms`).
7. Сверку «проём в геометрии ↔ коннектор в DA» пока делает только сборщик по построению; автоматическая проверка будет в S2-09.

## 8. Ручная проверка

Открой любой `LV_Docks_*` в редакторе (или PIE прямо в нём) и пройди через проёмы. Сетка `WorldGridMaterial` показывает метры, так что размер проёма и толщину стен видно на глаз.

## 9. Свет комнаты (S4-03, [ADR-0021](../ADR/ADR-0021-lighting-budget-procedural-look.md))

Бюджет — `DA_LightBudget` (`UHollowLevelMetrics::LightBudget`). Его проверяет Data Validation при сохранении уровня комнаты, `Hollow.Game.Light.RoomBudgets` и `Hollow.Light.Dump` в собранном рейде.

| Тип | Ламп | С тенью | Тень + мерцание | Light function | Объёмная тень |
|---|---|---|---|---|---|
| Spawn, Extraction, CoreVault, Hangar, Storage | ≤ 6 | ≤ 2 | ≤ 1 | ≤ 3 | ≤ 1 |
| Corridor, Junction | ≤ 3 | 0 | 0 | ≤ 2 | 0 |

Правила:
- Свет только подвижный: запечённого света нет (ADR-0008).
- Радиус лампы не больше диагонали комнаты.
- Мерцание — light function, не движение. Движущийся теневой свет каждый кадр сбрасывает кеш VSM.
- **Аварийная лампа** в каждой комнате: точечная, без тени, `M_LF_Emergency`.
- **Теневые лампы** — потолочные панели (Rect Light), в проходных комнатах без тени.
- Отделка только из движковых примитивов, без коллизии, `CanEverAffectNavigation = false`, вне проёмов и сокетов.
- Материалы — инстансы `M_Hollow_Surface` и `M_Hollow_Emissive`, своих текстур не завозим.
- Свет, отделку и маркер `HollowLightingSpec` ставит `create_lighting_assets.py`. Правка руками будет перезаписана при следующем изменении спецификации: меняй спецификацию в скрипте.
